# Blackwell subsystem verification

## Running the suites

Run these commands from the repository root on the RTX 5080 verification host. The v1 acceptance configuration shares the wide/K32 arithmetic pipeline. The dot suite also exercises the experimental independent configuration.

| Command | What it checks |
| --- | --- |
| `test/run.sh lint` | Verilator elaboration and lint of the subsystem top using the production file list. |
| `test/run.sh unit` | Self-checking SystemVerilog benches, both dot configurations, simulation-assertion cases, and the SMEM/TMA/mbarrier cocotb integration tests. |
| `test/run.sh workloads` | One top-level model shared by linear replay, commit ordering, accumulation, FA4 timing and FA4 replay. |
| `test/run.sh all` | Lint, unit and workloads in sequence. |
| `test/synth/check.sh` | Slang elaboration of the top and Yosys synthesis/check of the FIFO, SRAM, TC bridge, TC tracker and INT8 dot in the ORFS image. |

Set `JOBS` to control build parallelism. Set `ALLEGRO_BUILD_DIR` to select the regression output directory. The [dot suite](dot/run.sh) also accepts `MMA_SIM_VECTORS`, a file of additional numerical transactions in the existing 17-field [reference format](dot/reference.py). External finite cases must share the decode, zero-term, alignment and packing rules of the DUT. [MMA-Sim finite accumulation reference](https://github.com/yuhin777/Allegro/blob/ac5b2a4/MMA-Sim/mmasim/simulator/arithmetic.py)

The dot array bench drains between three phases. The numerical phase compares all 64 result cells by tag under intermittent backpressure. The throughput phase keeps the sink ready and requires 96 consecutive input handshakes. The latency phase issues four isolated requests and measures each family from acceptance to result transfer. External vectors extend the numerical phase. To inspect a phase, run `python3 test/dot/reference.py --phase numerical`, `--phase throughput` or `--phase latency` from the repository root. Invoking the generator without arguments prints all three in execution order.

## Testbench architecture

Place a module interface or pipeline-edge test beside the benches for that DUT. Use the workload suite for commands that cross subsystem boundaries, memory visibility and kernel replay. The module test plan below links each specification to its executable checks and pass conditions.

| Responsibility | What the test author supplies |
| --- | --- |
| Scenario | A legal initial state, an ordered sequence of transactions, the exact backpressure or assertion point, and the observable outcome that would expose a defect. |
| Environment and driver | Assemble the DUT and its external services. Encode requests, hold each offer until acceptance, and bound waits for a response. The top-level driver owns clock advancement. |
| Monitor | Sample accepted transfers on the specified edge. Record identity, payload and cycle for each event used in a check. |
| Reference and checker | Derive the expected value or ordering from the specification and compare it with the observed event. Track write acceptance, write ACK and software completion separately when the contract distinguishes them. |
| Runner | Select suites and configurations, build the model, run the named cases and report their results. Specify stimulus phases and timing conditions inside the test. |

A workload supplies its memory model and owns its address layout, input generation and service assumptions. Shared protocol code depends only on the DUT interface. Before sharing a helper, compare field widths and signedness, reset behavior, sampling phase and the edge that consumes a response.

A small SV bench can own all these responsibilities in one file. In the base bench, each input holds its pending byte independently. The reference queues advance on handshakes and predict occupancy and head data even while a FIFO is full. A reviewer can trace the simultaneous pop and push from stimulus to the comparison on the next edge. [FIFO and pipeline bench](base/base_tb.sv)

For a top-level example, the linear environment supplies a read-only GMEM model. The scenario issues four copies in each of two phases, waits for the barrier, reads the destination through LSU and compares each word with the expected sequence. The same scenario checks the observed ordering requests through close. [Linear environment](workloads/linear_driver.py) · [Linear replay](workloads/linear_replay.py)

For larger environments, OpenTitan SPI_HOST illustrates separate stimulus, monitoring and scoreboarding. The cocotb AXI FIFO example assembles a master and a RAM model and checks the destination bytes under backpressure. [OpenTitan SPI_HOST verification](https://opentitan.org/book/hw/ip/spi_host/dv/index.html) · [AXI FIFO cocotb bench](https://github.com/alexforencich/verilog-axi/blob/master/tb/axi_fifo/test_axi_fifo.py)

## Writing and interpreting tests

- Start with a rule in the owning specification. Give the legal starting state, stimulus and observable pass condition. Use an SV bench for a module's signal or edge contract and cocotb for cross-module transactions, memory contents and kernel replay. The tables identify the executable checks. A **planned** item names a check that still needs a dedicated executable case. [OpenTitan verification methodology](https://opentitan.org/book/doc/contributing/dv/methodology/index.html)
- Sample ready/valid transfers on the rising edge with both asserted. During a stall, check that valid and payload hold. Track the original transaction ID through completion and check exactly-once delivery. Observe request acceptance, actual write, ACK, notification and record reuse separately when their edges differ. [Common protocol](../doc/rtl_specs/top/blackwell_async_subsystem_top.md#common-protocol)
- Derive expected values from logical coordinates or an independent arithmetic reference. Compare the specified bits or bytes, including unselected bytes when testing masks. State the rounding and tolerance for an approximate software reference.
- For a cycle assertion, specify the starting handshake, warmup, input readiness and sink service. Bound waits for an expected event. On failure report the case, cycle, transaction or coordinate, expected and observed values, and any seed or parameters needed to reproduce it.
- Report lint, unit simulation, replay results, cycle assertions and synthesis separately. Record whole-kernel elapsed cycles as observations. A timing pass names the checked edges and the service conditions.

### SMEM, TMA and memory barriers

The [SMEM subsystem scenarios](tma/smem_subsystem_tests.py) exercise tensor addressing, copy throughput, store groups and barrier waits. Their [fabric driver](tma/smem_fabric_driver.py) drives the clock and ports, serves GMEM and ordering responses, and records handshakes. `fifo_ticket_holds_until_command_transfer` fills the ingress FIFO and releases a preferred ticket while the next command is stalled. `service_driver_samples_only_transferred_lanes` stalls an ordering request and one of two SMEM read-return groups, then checks when each transaction is recorded. The bound setup product checker runs in the same model. Seven [negative cases](tma/run_assertions.sh) run in separate simulations and require the designated assertion for each illegal opcode, map alignment, unsolicited return, malformed descriptor or expanded address overflow.

| [Linear replay](workloads/linear_replay.py) | `open_response_holds_until_accepted`, `close_drains_queued_wait`, `close_flushes_both_halves_before_ordering` | A stalled open response holds issue closed.
